# 10. 절대 하지 말아야 할 것 / 반드시 유의할 것

## 10-1. 절대 하지 말아야 할 것
### 고객 인증/로그인
- 고객용 아이디/비밀번호 로그인 만들지 말 것
- 이름 + 생년월일 로그인 만들지 말 것
- 고객 회원가입 절차를 길게 만들지 말 것

### 앱 구조
- 설계사별 앱 따로 만들지 말 것
- 고객별 앱 따로 만들지 말 것
- 링크가 앱 빌드에 박히는 구조로 만들지 말 것

### UI/UX
- 고객 앱에 메뉴를 많이 넣지 말 것
- 청구 요청 입력 폼을 복잡하게 만들지 말 것
- 고객이 소식지를 직접 구독 선택해야 보이는 구조로 만들지 말 것

### 데이터/서버
- 요청과 파일을 한 덩어리로 대충 저장하지 말 것
- storageKey 검증 없이 파일 저장 확정하지 말 것
- 연결 안 된 기기에서 요청 생성 허용하지 말 것
- 상태 변경 이력 없이 상태만 덮어쓰지 말 것

### 푸시
- 무조건 푸시 보내지 말 것
- 내부용 글까지 고객에게 푸시하지 말 것
- 푸시 실패 때문에 본 기능이 막히게 만들지 말 것

---

## 10-2. 꼭 이렇게 해야 하는 것
### 연결
- 고객 링크는 반드시 customer_id 기준으로 생성할 것
- 연결 시 `agent_id + customer_id + device_id`를 함께 저장할 것
- 고객 앱 상단에 연결된 설계사명/고객명을 표시할 것

### 파일
- presign → 업로드 → 요청 저장 흐름을 명확히 분리할 것
- 파일 유형/용량 검증을 서버에서도 할 것
- 파일 경로 prefix를 고객 청구용으로 분리할 것

### 요청
- 상태값을 정해진 값만 쓰게 할 것
- 상태 변경 시 로그를 남길 것
- 설계사 화면에서 고객 식별이 명확하게 보이게 할 것

### 소식지
- 기존 설계사 게시판 중 고객 노출 대상만 고객 앱으로 내릴 것
- `agent_id` 기준 필터를 정확히 넣을 것
- 고객이 따로 고르지 않아도 자동 노출되게 할 것

### 운영
- 실패 로그를 남길 것
- 연결/재연결 시나리오를 꼭 테스트할 것
- 앱 삭제/재설치/기기 변경 테스트를 할 것

## 10-3. 개발자에게 주는 직접 지시
- 기존 프로젝트 구조를 최대한 존중해라.
- 명시된 범위 밖의 기능/레이아웃/권한 체계를 함부로 바꾸지 마라.
- 한 번에 크게 바꾸지 말고 단계별로 작게 완성해라.
- 각 단계가 끝날 때마다 “무엇을 구현했고 무엇을 아직 안 했는지”를 남겨라.
- 테스트 없이 다음 단계로 넘어가지 마라.
- 애매하면 UI보다 데이터 무결성을 우선해라.
