# 2. 아키텍처 및 구현 원칙

## 2-1. 전체 아키텍처 개요
구조는 크게 네 파트로 나뉜다.

1. **기존 설계사 앱**
   - 고객 선택
   - 링크 생성
   - 청구 요청 확인/처리
   - 고객용 소식지 등록

2. **고객 앱**
   - 링크 연결
   - 요청 생성
   - 파일 업로드
   - 요청 내역 조회
   - 소식지 확인
   - 푸시 수신

3. **서버/API**
   - 연결/요청/파일/소식지/푸시 처리
   - 권한 검증
   - DB 저장
   - R2 presign 및 저장

4. **스토리지/푸시**
   - R2: 고객 첨부 파일 저장
   - FCM/Expo Push: 푸시 알림 발송

## 2-2. 핵심 식별 원칙
고객 식별은 아래 3개 조합으로 고정한다.

- `agent_id`
- `customer_id`
- `device_id`

즉, “어떤 설계사의 어떤 고객이 어떤 기기에서 연결되었는지”를 서버가 알고 있어야 한다.

## 2-3. 연결 구조 원칙
앱은 하나만 배포한다.  
설계사별 앱, 고객별 앱, 링크가 박힌 전용 앱을 만들지 않는다.

연결은 다음 방식으로 한다.
- 설계사가 기존 앱에서 고객을 선택
- 링크 생성
- 고객이 앱 설치 후 링크 클릭
- 서버가 `device_id + agent_id + customer_id`를 저장
- 이후 고객 앱은 저장된 연결을 사용

## 2-4. UI/UX 원칙
### 고객 앱 UX
- 고객이 직접 고민하면 실패한다.
- 가능한 한 입력 항목을 줄인다.
- “사진 올리고 보내기”가 핵심이다.
- 소식지는 자동 노출한다.
- 고객에게 설정을 많이 요구하지 않는다.

### 설계사 앱 UX
- 기존 고객 관리 흐름을 해치지 않는다.
- 새로운 메뉴는 최소로 추가한다.
- 고객 요청은 고객 목록과 자연스럽게 연결되어야 한다.
- 상태값으로 운영 가능해야 한다.

## 2-5. 반드시 지켜야 할 구현 원칙
- 기존 고객 DB를 최대한 활용한다.
- 고객 요청과 요청 첨부 파일을 테이블 분리한다.
- 파일 업로드는 DB 저장 전후 상태가 추적 가능해야 한다.
- 연결 해제/재연결 흐름을 미리 고려한다.
- 앱 삭제/재설치/기기 변경 케이스를 고려한다.
- 푸시는 이벤트 2종 중심으로만 시작한다.
- 운영 로그를 남겨 추적 가능하게 한다.

## 2-6. 절대 하면 안 되는 것
- 고객 앱에 아이디/비밀번호 회원가입 넣기
- 이름 + 생년월일만으로 로그인시키기
- 설계사별 앱 만들기
- 고객이 소식지를 직접 구독 설정해야만 보이게 만들기
- 청구 요청 기능에 과도한 입력 폼 넣기
- 푸시를 마구 발송하기
- 기존 설계사 앱의 다른 메뉴/레이아웃을 광범위하게 개편하기
- 요청 생성과 파일 업로드를 한 트랜잭션처럼 막 섞어서 불안정하게 만들기

## 2-7. 단계별 개발 원칙
항상 아래 순서로 개발한다.

1. DB
2. 연결 구조
3. 파일 업로드
4. 요청 생성/조회
5. 설계사 메뉴
6. 소식지 연결
7. 푸시
8. UI/UX 정리
9. QA 및 운영 안정화

UI부터 만들지 말고 데이터 흐름부터 만든다.
