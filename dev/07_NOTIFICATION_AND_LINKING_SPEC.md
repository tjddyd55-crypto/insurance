# 7. 연결 구조 / 링크 / 푸시 / 파일 저장 구조

## 7-1. 링크 구조
앱은 공용 하나다.  
연결은 링크로 처리한다.

### 링크 예시
- Universal Link: `https://domain.com/customer-app/connect/ABC123XYZ`
- Deep Link: `myapp://connect/ABC123XYZ`

### 원칙
- 링크는 설계사 앱에서 고객별 생성
- 고객별 `customer_id`가 이미 매핑된 링크여야 함
- 고객이 링크를 누르면 앱이 열리고 연결 처리

## 7-2. 연결 데이터 흐름
1. 설계사가 고객 선택
2. 링크 생성
3. 고객이 링크 클릭
4. 앱에서 `device_id` 수집
5. 서버로 `linkCode + deviceId` 전송
6. 서버가 `agent_id + customer_id + device_id` 저장
7. 고객 앱 전용 토큰 발급
8. 이후 모든 조회/생성은 이 토큰으로 수행

## 7-3. 연결 유지 정책
### 기본
- 연결은 계속 유지
- 앱 삭제, 기기 변경, 강제 해제 전까지 유지

### 끊기는 경우
- 앱 삭제 후 재설치
- 폰 변경
- 관리자가 연결 해제
- 보안 정책상 강제 만료

### 대응
- 설계사 다시 연결 버튼 제공
- 재발급 링크 허용

## 7-4. 파일 저장 구조
스토리지는 기존 R2 구조를 재사용한다.

### 권장 키 구조
`customer-claims/{agentId}/{customerId}/{requestId-or-temp}/{uuid}-{originalName}`

### 원칙
- 고객 요청 파일은 기존 다른 파일과 prefix를 분리
- 고객용 파일 저장 경로를 명확히 구분
- 임시 업로드 후 request 생성 시 최종 매핑해도 됨
- 파일 메타는 DB에 저장

## 7-5. 파일 업로드 구현 유의점
- 파일 업로드 성공 후에만 DB row를 만들 것 또는 생성 API 내에서 유효한 storageKey만 반영할 것
- 미완료 업로드의 orphan 정리 정책 고려
- 악성 파일/확장자 검증
- Content-Type과 확장자 모두 검증
- 용량 제한 명확히

## 7-6. 푸시 알림 정책
### 초기 이벤트 2개만
1. 설계사 소식지 등록
2. 고객 요청 상태 변경

### 푸시 대상
- 연결된 고객 중 active device/push token만
- agent_id/customer_id 기준 발송

### 절대 하지 말 것
- 청구 요청 생성 즉시 고객에게 자기 자신한테 알림 보내기
- 모든 글마다 과도하게 푸시
- 내부 게시물까지 고객에게 푸시

## 7-7. 소식지 노출 정책
- 고객 앱은 연결된 설계사의 고객 노출용 게시물만 본다.
- 고객이 구독할 설계사를 따로 선택하지 않는다.
- 설계사 내부 글/관리 글은 노출 금지
- 중요 공지 pinned 지원 권장

## 7-8. 운영상 주의점
- 잘못된 고객에게 링크를 보내지 않도록 설계사 앱에서 고객명 강조
- 고객 앱 상단에 연결된 설계사명/고객명 표시
- 연결 오류 시 설계사에게 재연결 안내 가능해야 함
- 연결 로그와 요청 생성 로그는 반드시 남길 것
