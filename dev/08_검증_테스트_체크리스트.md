# 08. 검증 / 테스트 체크리스트

## 기본 실행 검증

프로젝트에 맞는 명령어로 아래를 실행한다.

예시:

```bash
npm run lint
npm run build
npm test
node --check server/apis/추가한파일.js
```

프로젝트에 lint/test가 없으면 최소한 추가한 server 파일에 대해 문법 검사를 한다.

## 브랜치 확인

```bash
git branch --show-current
```

반드시 새 브랜치여야 한다.

예:

```text
feature/self-sms-contract-signature
```

## 관리자/FC API 검증

### 템플릿 생성

```http
POST /api/admin/contracts/templates
```

성공해야 함.

### 좌표 필드 저장

```http
POST /api/admin/contracts/templates/:id/fields
```

성공해야 함.

### 템플릿 active 변경

```http
PATCH /api/admin/contracts/templates/:id/status
```

성공해야 함.

### 패키지 생성

```http
POST /api/admin/contracts/packages
```

성공해야 함.

### 발송 세션 생성

```http
POST /api/admin/contracts/send-sessions
```

성공해야 함.

확인:

```text
linkCode 생성
target_phone_masked 저장
target_phone_hash 저장
문서 수만큼 contract_document_instances 생성
```

## 고객 링크 검증

### 링크 조회

```http
GET /api/contracts/public/:linkCode
```

확인:

```text
maskedPhone 표시
documents 목록 표시
identityVerified false
```

### OTP 발송

```http
POST /api/contracts/public/:linkCode/otp/send
```

확인:

```text
phone body 없이 동작
저장된 지정번호로 발송 처리
otp_hash 저장
otp_sent_at 저장
otp_expires_at 저장
```

### phone 조작 차단

아래 요청은 400 처리되어야 함.

```json
{
  "phone": "01099999999"
}
```

### OTP 검증

```http
POST /api/contracts/public/:linkCode/otp/verify
```

성공 후 확인:

```text
identity status verified
provider self_sms
level phone_possession
send_session status identity_verified
```

## 인증 전 차단 검증

OTP 인증 전 아래 API는 실패해야 한다.

```text
GET /documents/:documentInstanceId
POST /documents/:documentInstanceId/values
POST /documents/:documentInstanceId/sign
POST /complete
```

예상 상태:

```text
403
```

## 문서 상세 검증

OTP 인증 후 문서 상세 조회 성공.

확인:

```text
PDF 정보 반환
fields 반환
values 반환
document status viewed
```

## 입력값 저장 검증

```http
POST /api/contracts/public/:linkCode/documents/:documentInstanceId/values
```

확인:

```text
fieldKey 검증
값 저장
status input_saved
```

## 서명 검증

```http
POST /api/contracts/public/:linkCode/documents/:documentInstanceId/sign
```

확인:

```text
agreed false면 400
agreed true면 성공
손사인 저장
signature value 저장
document status completed
signature_evidences 생성
evidence_hash 생성
```

## 여러 문서 검증

계약서 3개 패키지를 만든다.

확인:

```text
document_instances 3개 생성
첫 번째 문서 완료해도 전체 send_session은 completed 아님
필수 문서 모두 완료 후 complete 가능
선택 문서 미완료여도 complete 가능
```

## 전체 완료 검증

```http
POST /api/contracts/public/:linkCode/complete
```

미완료 필수 문서가 있으면 400.

모든 필수 문서 완료 후:

```text
send_session status completed
completed_at 저장
```

## 중복 방지 검증

1. 같은 document sign API 두 번 호출
2. 같은 complete API 두 번 호출
3. OTP verified 후 다시 verify 호출

기대:

```text
중복 데이터 생성 없음
사용자에게는 이미 완료됨 또는 성공 상태 반환
```

## 보안 검증

- public API에서 다른 documentInstanceId 접근 차단
- 다른 linkCode의 documentInstanceId 접근 차단
- expired/cancelled 세션 접근 차단
- OTP 원문 DB 저장 없음
- 휴대폰번호 전체 화면 노출 없음
- 운영환경에서 OTP 콘솔 출력 없음
- 운영환경에서 mock 인증 없음

## 운영 DB 반영 시 참고

- `signature_evidences`에 **`uq_signature_evidences_document_instance_id`**(부분 유니크)를 두었다. 동일 `document_instance_id`로 증빙 행이 이미 2건 이상 있는 DB에서는 **인덱스 생성이 실패**할 수 있다. 배포 전 `document_instance_id` 기준 중복 행을 정리할 것.
- `ensureContractSelfSmsSchema`는 `CREATE TABLE IF NOT EXISTS` 및 `ADD COLUMN IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS` 위주로 **init 반복 실행에 안전**하도록 맞춰 두었다.

## 최종 완료 기준

아래 시나리오가 한 번에 성공하면 완료.

```text
1. 새 브랜치 확인
2. PDF 계약서 템플릿 생성
3. 좌표 필드 저장
4. 패키지 생성
5. 고객에게 발송 세션 생성
6. 고객 링크 접속
7. 마스킹 번호 확인
8. 인증번호 받기
9. OTP 검증
10. 문서 목록 확인
11. 문서 상세 확인
12. 손사인
13. 문서 완료
14. 모든 필수 문서 완료
15. 전체 완료
16. signature_evidences evidence_hash 확인
17. 기존 손사인/PDF좌표/고객관리 기능 깨짐 없음
```
